# AI開発ワークフロー（全プロジェクト共通）

最終更新：2026-08-25

このファイルは**特定のプロダクトに依存しない**開発の進め方を定める。
別のリポジトリへそのままコピーして使える内容だけを書く。

## この文書の位置づけ（二層構造）

| ファイル | 中身 | 新しいプロジェクトでは |
|---|---|---|
| `docs/ai-development-workflow.md`（本書） | **どう進めるか**。共通の手順・停止条件・完了条件 | そのままコピーして使う |
| `docs/project-profile.md` | **このリポジトリ固有の事実**。技術構成・DB・認証・外部サービス・既知制約・保留課題 | プロジェクトごとに作り直す |

作業を始める前に、必ず両方に目を通す。
本書に書かれた手順と、`project-profile.md` に書かれた事実が矛盾する場合は、
どちらも書き換えずに報告する。

---

## 0. SAFE CHECKPOINT（大きな作業を始める前に）

作業開始前に、必ず次を確認して報告に含める。

- 現在の branch
- HEAD のcommit hash
- working tree が clean か（未コミットの変更を勝手に破棄しない）
- リモートと同期しているか

**working tree が clean な commit を「安全な戻り地点」とする。**
ここが定まっていない状態で大きな変更に入らない。作業が失敗しても、
この地点まで確実に戻れることが分かっていれば、思い切って進められる。

---

## 1. リスク分類（A / B / C）

作業を始める前に、依頼内容がどれに当たるかを判断する。
**判断に迷ったら、ひとつ上のリスクとして扱う。**

### A：低リスク（自走してよい）

画面表示・レイアウト・軽微なフロントエンドの変更、既存API/RPCをそのまま使う変更、
読み取り中心の変更など。データの持ち方も、保存の形も変えないもの。

```
SAFE CHECKPOINT → 調査 → 想定内なら最小実装 → test → build → lint → commit
```

**途中確認を必要以上に求めず、最後まで進めてよい。**

### B：中リスク（自走してよいが、検証と後片付けまでやりきる）

既存のDB構造・RLS・RPCをそのまま使う新機能、利用者固有データを扱うもの、
実環境での書き込み確認が必要なもの。

```
SAFE CHECKPOINT → 調査 → 最小実装 → mock検証 → E2E → 次回利用テスト
→ test / build / lint → commit → 実環境確認 → cleanup → 最終確認
→ 必要なら検証記録のcommit → push前で停止
```

**既存のDB設計を変えずに実現できるなら、停止条件に触れない範囲で自走する。**
実環境への書き込みを伴う確認は、事前に許可を得てから行う（→ 第8章）。

### C：高リスク（承認前に実装しない）

migration、RLSの変更、RPC定義の変更、認証方式の変更、既存データの一括変換、
カラム削除、保存形式の変更、後方互換性に影響する変更、大規模リファクタ。

```
SAFE CHECKPOINT → 調査 → 影響範囲の確認 → 修正案の提示 → STOP
```

**承認を得るまで実装しない。** SQLファイルの作成までは行ってよいが、適用はしない。

---

## 2. 調査と実装を必要以上に分断しない

「まず調査だけ」→ 報告 →「では実装」という往復を毎回繰り返さない。
往復そのものが時間を消費し、調査で分かったことが次の依頼までに劣化する。

**標準ルール：**

> まず現状を確認する。
> 想定内で、既存設計を壊さずに実現できる場合は、そのまま最小実装まで進む。
> 停止条件に該当した場合のみ、変更せずに停止する。

ただし、実装に入る前に「現在の構造 / 今回変更するファイル / 変更しない部分」を
**短く宣言してから**着手する。これは確認待ちではなく、認識ずれを早く見つけるためのもの。

---

## 3. 必ず停止する条件

次のいずれかに当たったら、その場で手を止める。**修正を重ねない。**

1. migration が必要
2. RLS の変更が必要
3. 認証方式の変更が必要
4. 既存データの削除・一括変換が必要
5. 保存形式・後方互換性を壊す可能性がある
6. 調査結果が当初の想定と大きく異なる
7. データ損失の可能性がある
8. test / build の失敗が最小修正で解消できない
9. 実環境で想定外のレスポンス・権限エラー・DB構造の差異が出た
10. 同種の不具合・手戻りが2回以上発生した（→ 第4章）

### そのほか、必ず承認を得てから行うこと

停止条件とは別に、次は「戻せない」または「外に影響が出る」ため、
指示があっても実行前に必ず確認を取る。

- 本番環境へのデプロイ
- **課金が発生する操作**
- **外部サービスへの公開**（他者から見える場所に出す行為）
- secrets・APIキーの表示や変更
- 未コミット変更の破棄、履歴を書き換えるGit操作

### 停止したときの報告

次を**分けて**書く。混ぜない。

- **事実**：実際に読んだコード・実行結果・レスポンス（推測を混ぜない）
- **推測**：まだ確認していない仮説（「未確認だが」と明示する）
- **根本原因**：症状ではなく、なぜそうなるのか
- **再現方法**：手順
- **影響範囲**：どこまで及ぶか
- **最短の修正案**
- **必要なら最小範囲の再構築案**

「事実」と「推測」を曖昧にした報告はしない。判断を誤らせる。

---

## 4. 同種の不具合が2回続いたら、全体を監査する

同じ種類の不具合や手戻りが2回以上続いた場合、**局所修正を続けない。**
3回目の局所修正は、たいてい4回目を呼ぶ。

いったん停止して、次を通しで見る。

- データフロー（どこで生まれ、どこを通り、どこに保存されるか）
- 状態管理（どこが正本か）
- コンポーネントの境界
- DBとの境界
- 認証・セッション
- mock と実環境の差
- 再現条件
- 既存設計との不整合

そのうえで、次のどれが最短かを判断して提示する。

- **A. 個別修正を続ける**
- **B. 構造を直す**
- **C. 最小範囲を作り直す**

---

## 5. Definition of Done（「次回利用」まで含める）

**「今、一度動いた」で完成にしない。** 可能なものは次まで確認する。

```
初回利用 → 保存 → 戻る → 再訪 → 翌日・次回の利用を想定 → 同じデータを再利用
```

「初回は使えるが、翌日もう一度使おうとすると使いづらい」という種類の問題は、
初回実装の時点で見つける。あとから見つかると、設計に戻る手戻りになる。

完了と報告してよいのは、次をすべて満たしたとき。

- 依頼内容がコードに反映されている
- 正常系・エラー系の両方を確認した
- **次回利用（再訪・再検索・再利用）を確認した**
- 既存機能の回帰を確認した（→ 第9章）
- 検証コマンド（`project-profile.md` に記載）がすべて成功している
- 変更差分を自分で確認した
- プロダクトの不変条件に反していない（→ `project-profile.md`）

---

## 6. mock → 実環境の順で確認する

**実環境を最初のデバッグ場所にしない。** 実環境での試行錯誤は、
消せないデータと、原因の切り分けづらさを同時に生む。

### mock で確認すること

- 正常系
- エラー系
- 重複
- 再利用
- 次回利用
- 既存機能の回帰

### 実環境で確認すること

mockでは再現できない、**環境そのもの**に属するもの。

- RLS・権限
- 認証・セッション
- RPCの実際のレスポンス形式
- 外部キー制約
- 実DBの構造
- 外部サービスとの実通信

---

## 7. 最小変更

新しい仕組みを作る前に、既存のものを再利用できないか必ず確認する。

- component / API / RPC / DB / state / provider / 正規化処理 / ユーティリティ

**画面側で解決できることを、安易にDB変更で解決しない。**
DBの変更はリスク分類Cであり、承認と手戻りのコストが桁で違う。

判断の目安：「その値は本当にDBに無いのか、それとも画面が取りに行っていないだけか」

---

## 8. 実環境テストと cleanup をセットにする

実環境での確認を**始める前に**、次を決めて宣言する。

- 何を作るか
- 何を残すか
- 何を削除するか
- どうやって削除するか
- 削除できたことをどう確認するか

**標準の流れ：**

```
実環境確認 → 作成したIDを記録 → 検証 → 検証用データの cleanup
→ 残すデータの確認 → 読み取りのみで最終確認
```

**cleanup を別タスクとして後回しにしない。** 後回しにしたゴミは残る。

その他の原則：

- テスト用に**架空のデータを共有テーブルへ入れない**。実在するデータを使う
- 分からない項目を推測で埋めない（誤った値を残すより、空のほうがよい）
- 削除は、通常の利用者と同じ経路（権限が効いた状態）で行う。
  管理者権限での直接操作は、承認を得た場合に限る
- 削除の前に対象を必ず読み取って確認し、削除後に「消えたこと」と
  「消してはいけないものが残っていること」の両方を確認する

---

## 9. 回帰確認

新機能だけを見て終わらない。次の経路を通す。

- 入口（検索・一覧など、その機能に入る導線）
- 保存
- 再表示
- 戻る操作
- 再訪
- 主要な画面遷移

---

## 10. Git運用

```
SAFE CHECKPOINT → 実装 → test / build → commit
→ 必要なら実環境確認 → cleanup → 最終commit
→ push前で停止 → 確認 → push
```

- **commit と push を同じ判断にしない。** commitは自分の作業の区切り、
  pushは他者・他環境に影響を与える公開行為
- push は明示的な指示があるまで行わない
- 履歴の書き換え（squash・rebase・force push）は指示がない限り行わない
- commit は作業単位で分ける。1つのcommitに無関係な変更を混ぜない

---

## 11. 完了報告は簡潔にする

**正常終了時**は、原則これだけでよい。

1. 結果
2. 変更（作成・変更したファイル）
3. test / build / lint
4. DB変更の有無
5. 残課題
6. working tree
7. commit hash

- 既知の事項を毎回長く説明し直さない
- 詳細な報告は**問題が起きたときだけ**（→ 第3章の形式）
- 読み手が非エンジニアの場合は、専門用語を避けるか一言補足する

---

## 12. 既知事項を再調査しない

一度確認したことは記録し、次回ゼロから調べ直さない。
調べ直しは、最も気づきにくい時間の浪費になる。

`project-profile.md` に記録すべきもの：

- 外部APIの制約（使えること／使えないこと）
- mockの制約
- lint の baseline（既知の指摘）
- DB設計・テーブルの役割
- 認証方式
- 既知のバグと回避策
- 「壊してはいけない設計」

例外：外部サービスの仕様など**変わりうるもの**は、必要になった時点で再確認する。
そのときは記録も更新する。

---

## 13. 事実と推測を分ける

報告・調査メモでは常に区別する。

- **確認した事実**：実際に読んだコード、実行結果、レスポンス、スキーマ、文書の記載
- **推測**：まだ確認していない仮説

推測には「〜と思われる」「未確認だが」を付ける。曖昧なまま書かない。

---

## 14. 新しいプロジェクトでこの文書を使うとき

1. `docs/ai-development-workflow.md`（本書）をそのままコピーする
2. `docs/project-profile.md` をそのプロジェクト用に新しく作る
3. `CLAUDE.md`（または同等の指示ファイル）から両方を参照する

本書はプロダクトの内容に依存しない。特定のアプリ名・テーブル名・画面名が
本書に書き込まれていたら、それは `project-profile.md` に移すべき情報。
